# Cloud Worker Implementation Status

**Status:** pairing implementation and local hardening are complete; production exposure remains blocked on final runtime/deployment review.
**Branch:** `cloud/research`

## What the Worker establishes

- Cloudflare Worker in ES module TypeScript format.
- Wrangler JSONC configuration with a local D1 preview binding.
- Numbered D1 migrations under `cloud/worker/migrations/`.
- Workers Vitest integration using `@cloudflare/vitest-plugin` and Vitest 4.
- Automatic application of the D1 migrations in isolated test storage.
- Typed environment/binding definitions generated by Wrangler.
- JSON error envelope and defensive no-store response policy.
- Web Crypto SHA-256 credential hashing and bearer-token lookup.
- D1 schema-health checks.
- Atomic pairing bootstrap.
- Authenticated invitation creation/regeneration for the first device.
- One-time invitation acceptance with transactional second-device creation.
- Confirmation-code brute-force lockout.
- Coarse unauthenticated bootstrap rate limiting through a Cloudflare Rate Limiting binding.
- Input-size and JSON-shape validation for pairing endpoints.
- Reserved synchronization routes that return `501` until the sync protocol transactions are implemented.

## Deliberate non-goals

The current Worker does **not** implement message push, pull, ACK, R2 uploads, cleanup, or E2E encryption. Synchronization remains intentionally inactive; returning `501` is preferable to pretending to provide a partially correct sync service.

Pairing does not implement E2E cryptography. Device credentials, invitation tokens, and confirmation codes are only server-side authentication/bootstrap material.

## Local workflow

From `cloud/worker/`:

```bash
npm install
npm run migrate:local
npm run dev
npm test
npm run typecheck
```

The D1 local-development model uses Wrangler/Miniflare/workerd rather than a second hand-rolled SQLite server. Production resources are not touched by the local migration command.

## Current pairing guarantees

- Exactly one active device per participant is enforced by the D1 partial unique index.
- The authenticated device, not client input, determines relationship and participant identity.
- Invitation tokens and device credentials are stored only as SHA-256 hashes.
- Invitation acceptance is transactional and protected against concurrent acceptance.
- Consumed invitations cannot be replayed.
- Expired and locked invitations are rejected.
- Five invalid confirmation attempts trigger a 15-minute invitation lockout.
- Pairing JSON bodies are bounded to 16 KiB.
- Malformed, null, array, empty, and oversized pairing bodies are rejected.
- The pairing content type is restricted to `application/json` with optional parameters.

## Production safety

`wrangler.jsonc` contains a placeholder D1 database ID. No real Cloudflare database ID, account ID, secret, credential, or R2 bucket is committed. Production provisioning remains blocked until the final runtime/configuration review.

The bootstrap rate-limit namespace ID is currently `910001`. It must be confirmed to be unused in the target Cloudflare account before deployment.

## Current test coverage

The Worker tests cover:

- database health and schema presence;
- bearer authentication and credential hashing;
- atomic bootstrap;
- valid acceptance and replay rejection;
- expired invitations;
- invitation regeneration;
- concurrent acceptance with exactly one winner;
- malformed and oversized request bodies;
- strict JSON content-type handling;
- confirmation-code lockout and recovery;
- rejection of invitation creation by the joining device;
- defensive response headers;
- disabled synchronization endpoints.
