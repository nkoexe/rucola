# Rucola Cloud Protocol Hardening Review

**Status:** C1 adversarial protocol review completed; the reviewed protocol is now substantially implemented and has received follow-up hardening. Final two-device semantics are still pending PR #15 validation.

**Implementation branch:** `cloud/research`

**Current hardening branch:** `fix/cloud-mailbox-direction` (PR #15, open)

**Purpose:** Record the protocol failure scenarios, hard invariants and implementation decisions that protect the Worker/D1/R2 synchronization boundary.

## 1. Current conclusion

The Workers + D1 + R2 architecture remains the active direction. The phone's local SQLite remains the permanent source of truth.

The major C1 findings have been translated into implementation and tests:

- durable client message IDs and sender sequences;
- transactional server sequence allocation and message acceptance;
- idempotent push/retry semantics;
- durable message receipts;
- directional pull/ACK hardening in PR #15;
- media reservation/upload/completion lifecycle and database invariants;
- finite mailbox/receipt retention;
- bounded pull batches and cursor validation;
- device-bound authentication and separate future encryption identity.

The remaining uncertainty is no longer whether the basic protocol can be implemented. It is the final production policy and integration work: directional two-device validation, exact retention policy reconciliation, poison-message handling policy, deployment/operational hardening, and mobile integration.

## 2. Locked protocol invariants

### Message identity

- `message_id` is generated by the sender before the first push.
- `message_id` never changes across retries.
- `(relationship_id, message_id)` is unique.
- sender device + sender sequence identify the sender-side ordering primitive.
- conflicting reuse of a message identity or sender sequence is rejected.

### Sender order

The client allocates sender sequence numbers durably so offline bursts retain their original sequence numbers across retries.

### Server order

- `server_seq` is allocated only for a genuinely new accepted message;
- it is unique within a relationship;
- it is monotonically increasing for accepted messages;
- it represents acceptance order, not client creation time;
- a retry returns the original server sequence.

### Immutability

After acceptance, ciphertext and immutable message metadata cannot be replaced. Only lifecycle/receipt metadata may change.

### ACK

ACK means the recipient has durably persisted the covered partner-originated messages and any required media locally. It does not mean displayed, opened, read or notified.

ACK is idempotent and safe to retry after a lost response.

### Local durability

The recipient must commit message application and its durable cursor before sending the corresponding ACK.

## 3. Directional mailbox correction

The original implementation accidentally modeled mailbox pull/ACK too broadly: a device could observe or acknowledge messages that it had itself sent.

PR #15 corrects this by making delivery/acknowledgement directional:

```text
Device A sends → mailbox
Device B pulls  → A's messages
Device B ACKs   → A's messages
```

A device must not treat its own sent copies as partner deliveries.

The PR also adds delivery-to-device receipt metadata and replaces same-device tests with genuine two-device scenarios, including interleaved sender/cursor coverage.

Until PR #15 is merged and its CI/test result is confirmed, this directional behavior is a pending hardening change rather than a completed production invariant on `cloud/research`.

## 4. Failure matrix

| Failure | Required behavior |
|---|---|
| Push request times out after server commit | Retry same `message_id` + `sender_seq`; return original acceptance. |
| Same message pushed twice | One mailbox acceptance only. |
| Same sender sequence with different message ID | Reject as sequence conflict. |
| Recipient crashes before SQLite commit | No ACK; message remains available within retention. |
| Recipient commits then ACK fails | Retry ACK; duplicate ACK is harmless. |
| Media upload succeeds but message push fails | Temporary upload is eventually expired. |
| Media completion/upload expires | Client must create or retry a valid upload within its lifetime. |
| Media object missing when pulled | Do not ACK; treat as a recoverable integrity/media failure. |
| Invitation accepted twice concurrently | One acceptance consumes the invitation. |
| Invitation expires during acceptance | Server-side expiry check decides; client clock is irrelevant. |
| Device credential revoked | Authenticated operations fail. |
| Client clock is wrong | Server sequence remains authoritative for mailbox traversal. |
| Server unavailable | Local outbox remains pending; local history is preserved. |
| Mailbox retention expires | Delivery is no longer guaranteed; expiry must not silently create a second acceptance. |
| Malformed/corrupt ciphertext | Recipient must not ACK unverifiable data; poison-message handling must not silently discard it. |

## 5. Offline burst semantics

```text
Sender locally creates:
A sender_seq=1
B sender_seq=2
C sender_seq=3

Recipient reconnects later.

Server accepts each message with its own server_seq.
Recipient persists A/B/C in order.
Recipient ACKs only after durable local commit.
```

The client retains original IDs and sender sequences. The server sequence is acceptance order and must not be used to pretend to reconstruct client creation order.

## 6. Media protocol

Media is an independent temporary resource:

```text
POST /v1/media/... create/reserve
        ↓
PENDING
        ↓
PUT upload
        ↓
POST .../complete
        ↓
READY
        ↓
POST /v1/sync/push referencing media upload
        ↓
ATTACHED mailbox message
```

The Worker enforces relationship/device ownership and requires `READY` media before a `PHOTO_VIDEO` message can be accepted. R2 stores bytes; D1 controls lifecycle and authorization metadata.

Current server limits are 20 MB images and 100 MB videos.

## 7. Pull/ACK semantics

Pull is non-destructive. The client uses a durable high-water cursor.

The intended sequence is:

```text
pull after cursor
      ↓
validate/decrypt/download required media
      ↓
SQLite transaction
      ├─ persist inbound message(s)
      ├─ update active/history state
      └─ advance durable cursor
      ↓
COMMIT
      ↓
ACK covered partner messages
```

The mobile `SyncEngine` implements the local transaction/cursor/ACK structure for the text/emoji path. It currently blocks media synchronization and does not yet run as part of the application lifecycle.

## 8. Corrupt/poison messages

The protocol requires bounded pulls and forbids acknowledging an item that has not been durably accepted. The exact user-facing repair/dead-letter policy remains an open product/implementation decision.

Do not silently discard a permanently invalid message.

## 9. Pairing

The human-facing mechanism is **five emojis**. The technical invitation token is a separate high-entropy credential with expiry and bounded confirmation attempts.

The mobile transport for pairing exists in `CloudClient`, but onboarding has not yet integrated it.

## 10. Retention

The current Worker code uses a **7-day mailbox retention window**. Older review/architecture text used 14 days; the implementation now needs to be treated as authoritative until the product explicitly decides otherwise.

Durable message receipts have a separate finite retention period. The current hardening documentation describes 30 days after acceptance, but this should be reconciled against the deployed schema and cleanup behavior before calling the contract final.

## 11. E2E

The transport intentionally treats message payloads as opaque. The final cryptographic protocol/library is not selected yet.

Do not use bearer device credentials as encryption keys and do not implement custom cryptography as a substitute for the final protocol.

Any future protocol change must update the implementation tests and this document together. Do not allow an old protocol assumption to survive only in documentation or test fixtures.
