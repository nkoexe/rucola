# Rucola Cloud Protocol Hardening Review

**Status:** C1 adversarial protocol review complete; implementation still intentionally blocked.

**Branch:** `cloud/research`

**Purpose:** Try to break the proposed mailbox protocol before Worker/D1/R2 implementation. This document records the failure scenarios reviewed, the required invariants, findings, and protocol changes that must be reflected in the implementation.

## 1. Review conclusion

The overall architecture survives the adversarial pass: Workers + D1 + R2 remains appropriate, and SQLite on the phone remains the permanent source of truth.

However, the first architecture draft exposed several protocol-level issues that should be fixed before implementation:

1. **Media upload ordering was internally inconsistent.** A media row cannot require a foreign key to a mailbox message if the media upload is created before the mailbox message exists. Media needs an upload-session/lifecycle state that can exist before message attachment, or the message must be created first.
2. **`server_seq` allocation needs an explicit per-relationship counter/transaction strategy.** The schema mentioned atomic allocation but did not contain the counter needed for a concrete implementation.
3. **Sender sequence numbers are a client-side durable protocol primitive.** They cannot be generated ad hoc in memory. The local database must allocate/persist them transactionally with the outgoing message.
4. **Duplicate/idempotent push needs explicit response semantics.** A retry with the same message ID/sequence must return the original acceptance, while a reused sender sequence with a different message ID must be rejected as a protocol conflict.
5. **Media completion and message acceptance need a clear atomic boundary.** A message referencing media must never become deliverable while the referenced media is still only `PENDING`.
6. **ACK must remain independent from read state and must be idempotent.** This survives review and is now a hard invariant.
7. **Mailbox expiry creates an intentional delivery-loss boundary.** The product must explicitly accept that messages older than the maximum retention window cannot be delivered by the server.
8. **A permanently invalid/corrupt message must not block the mailbox forever.** The client needs a non-ACK error/repair path and bounded pull batches; the exact dead-letter behavior remains an implementation decision.
9. **Device authentication and encryption identity must remain separate.** Reinstall/recovery cannot be solved by treating the bearer token as an encryption key.

No finding requires changing away from Cloudflare D1/R2.

## 2. Hard invariants

These should become implementation-level tests, not merely documentation.

### Message identity

- `message_id` is generated by the sender before the first push.
- `message_id` never changes across retries.
- `(relationship_id, message_id)` is unique.
- `(relationship_id, sender_device_id, sender_seq)` is unique.
- Reusing an existing sender sequence with a different message ID is a conflict, never a second message.

### Sender order

For each sender device:

```text
sender_seq 41 -> 42 -> 43
```

must remain ordered even if HTTP requests arrive as 43, 41, 42.

The server may accept 43 before 41 if the client sends them out of order, but the client protocol must not *generate* out-of-order sequences for a normal offline burst. If strict contiguous delivery is desired, that must be an explicit server/client policy rather than an accidental consequence of arrival order.

### Server order

- `server_seq` is allocated only for a genuinely new message.
- It is unique within a relationship.
- It is monotonically increasing for accepted messages.
- It is receipt/acceptance order, not creation order.
- A retry returns the existing `server_seq`.
- It is never derived from client timestamps.

### Immutability

After message acceptance:

- ciphertext cannot be replaced;
- message type cannot be changed;
- sender identity cannot be changed;
- sender sequence cannot be changed;
- media reference cannot be silently redirected.

Only lifecycle metadata such as acknowledgement/expiry state may change.

### ACK

An ACK means:

> The recipient has durably persisted the complete message and any required media locally.

It does not mean displayed, opened, read, or notified.

ACK requests are idempotent. A lost ACK response must be safe to retry.

### Local durability

The recipient must not ACK between individual SQLite statements. Message insertion, active-slot replacement, history changes, and the local sync cursor/state must commit atomically before the ACK is sent.

## 3. Failure matrix

| Failure | Required behavior |
|---|---|
| Push request times out after server commit | Retry same `message_id` + `sender_seq`; server returns original acceptance. |
| Same message pushed twice | One mailbox row only. |
| Same sender sequence with different message ID | Reject as sequence/idempotency conflict. Do not create a second message. |
| Push batch partially fails | Client knows which messages were accepted/rejected; retry only unresolved items. No duplicate creation. |
| Recipient crashes before SQLite commit | No ACK; message remains available. |
| Recipient commits then ACK request fails | Retry ACK; duplicate ACK is harmless. |
| Media upload succeeds but message push fails | Orphan is cleaned up by explicit expiry/lifecycle. |
| Media upload URL expires | Request a new upload URL for the same logical upload if still valid. |
| Media object missing when message is pulled | Do not ACK; report a recoverable media error. Server must retain the mailbox item. |
| Media download succeeds but local persistence fails | Do not ACK; retry download/persistence. |
| Invitation accepted twice concurrently | Exactly one request consumes it; the other cannot create another participant/device. |
| Invitation expires during acceptance | Server checks expiry transactionally; client clock is irrelevant. |
| Device token revoked | All authenticated operations fail; no mailbox/media access. |
| Client clock is wrong | `client_created_at` is retained only as metadata; server order remains authoritative for mailbox traversal. |
| Server unavailable | Outgoing messages remain locally pending; no local data is lost. |
| Server is unavailable for weeks | Local history continues; delivery depends on explicit mailbox retention policy. |
| Malformed/corrupt ciphertext | Store only if structurally valid enough for mailbox handling; recipient must not ACK unverifiable data. Must not permanently block unrelated messages. |
| Relationship ended | Reject new sends; preserve local history; apply an explicit policy to already accepted mailbox items. |

## 4. Concurrency findings

### Concurrent pushes

D1's serialized writes are sufficient for allocating a relationship-scoped `server_seq` as long as the counter read/increment and message insert occur in one transaction.

Do not implement:

```text
SELECT max(server_seq)
→ increment in Worker memory
→ INSERT
```

because that creates a race in a general database design.

Preferred shape:

```text
BEGIN
  read current relationship sequence
  increment it
  insert mailbox row with allocated sequence
COMMIT
```

The exact D1 SQL/batch form should be tested against the deployed D1 behavior before production use.

### Duplicate push race

Two copies of the same HTTP request may arrive concurrently. The database uniqueness constraints must be the final authority. Application-level `SELECT` checks alone are insufficient.

The implementation should either:

- use an insert that cleanly detects the uniqueness conflict and then reads the existing row; or
- perform an equivalent transactional/idempotency pattern.

The client must never depend on a request reaching the Worker exactly once.

### ACK race

Two ACKs for the same message may arrive concurrently. The operation must be naturally idempotent via the primary key/unique constraint.

### Pairing race

Two accept requests for the same invitation must race on one transactional consumption condition. `consumed_at IS NULL` alone in application code is not enough unless the update/insert is atomic.

## 5. Offline burst semantics

Example:

```text
Sender offline locally creates:
A sender_seq=1
B sender_seq=2
C sender_seq=3

Recipient reconnects later.
```

The sender must push all three using their original IDs/sequences. The server assigns `server_seq` in acceptance order. Under normal client behavior this will be A, B, C.

If requests are reordered by the network, the protocol still must not create duplicates or rewrite sender sequence numbers.

For strict sender ordering at the mailbox boundary, a future implementation can reject/hold a message whose predecessor has not been accepted yet. This is **not required for basic idempotency**, but it is a product decision if server-side ordering must exactly match sender sequence despite arbitrary request reordering.

Recommendation for the first implementation: allow idempotent out-of-order acceptance but preserve `sender_seq` and make local history ordering explicitly sender-aware. Do not pretend that `server_seq` reconstructs original creation order.

## 6. Media protocol correction

The first architecture draft had a lifecycle contradiction:

```text
create media_objects row with message_id FK
→ upload media
→ create mailbox message
```

The foreign key makes this impossible because the mailbox message does not exist yet.

### Corrected model

Treat the media upload as an independent temporary resource first:

```text
POST /v1/media/uploads
        ↓
media upload session: PENDING
        ↓
presigned R2 PUT
        ↓
POST /v1/media/uploads/:id/complete
        ↓
media object: COMPLETE
        ↓
POST /v1/sync/push referencing media_id
        ↓
mailbox message accepted only if media_id belongs to the sender's relationship and is COMPLETE
```

The media table therefore needs to permit an unattached upload during its short pre-message lifetime. Options:

- nullable `message_id`, attached exactly once when the message is accepted; or
- a separate `media_uploads` table and a final `media_objects` row created during message acceptance.

**Recommendation:** use a separate `media_uploads` table if the implementation remains small enough. It makes lifecycle states explicit and prevents a half-attached `media_objects` row from being mistaken for a deliverable message.

The message push transaction should atomically attach the completed upload to the immutable mailbox message. A media ID must never be attachable to two messages.

The R2 object is still the bytes; D1 is the authorization/lifecycle metadata.

## 7. Media failure policy

### Upload completed, message not accepted

The upload remains temporary and is eventually expired. The client may retry the message referencing the same upload ID while it is still valid.

### Message accepted, R2 object disappears

This is a server-side integrity failure. The recipient must not ACK the message. The service should retain the mailbox record long enough to attempt repair/retry. Operational metrics should surface the inconsistency.

### R2 object exists, D1 upload record is missing

Treat it as an orphan. It is not deliverable. Lifecycle cleanup eventually removes it.

### Presigned URL leaks

The URL is a bearer capability. Keep it short-lived and avoid logging it. The R2 object must still be under an opaque key and inaccessible through the public bucket path.

## 8. Pull/ACK semantics

A pull cursor should represent the last server sequence that the client has **durably applied locally**, not merely the last sequence downloaded over HTTP.

Preferred client sequence:

```text
pull after cursor
      ↓
validate/decrypt/download required media
      ↓
SQLite transaction
      ├─ insert immutable message
      ├─ update active/history state
      └─ advance durable sync cursor
      ↓
COMMIT
      ↓
ACK server messages
```

If the app crashes before commit, the cursor does not advance and the server does not receive a durable ACK.

If the app crashes after commit but before ACK, the same message is safely re-read and the ACK is retried.

This gives the desired **at-least-once delivery + idempotent local application** model without making the server authoritative.

## 9. Corrupt-message / poison-message problem

A recipient that cannot decrypt or validate one mailbox message must not get stuck forever retrying the same message while newer messages are inaccessible.

The first implementation should therefore:

- pull bounded batches;
- identify messages individually;
- persist a local sync-error record for a permanently invalid item;
- avoid acknowledging an item that has not been durably accepted;
- continue processing independent later items where product semantics allow it;
- provide a future repair/retry path.

Whether the server eventually supports an explicit `REJECTED`/`UNDELIVERABLE` state is still open. Do not silently discard such messages.

## 10. Pairing findings

### Secure token

The invitation token remains the real credential for the pairing operation. It should have at least 256 bits of cryptographic entropy and be stored server-side only as a hash/HMAC-derived value.

### Human code

The human code is useful for confirmation but cannot be the sole secret if the security model says it is non-secret.

If manual code-only pairing is ever introduced, the protocol needs a separate rate-limited challenge mechanism and the code entropy must be evaluated as an actual authentication secret.

### Invitation consumption

Acceptance must be a single atomic state transition:

```text
UNCONSUMED + unexpired
        ↓
     CONSUMED
```

Creating the second device and consuming the invitation must occur in the same transaction. Otherwise a crash can leave a half-paired state.

---

## 11. Device lifecycle findings

For MVP:

- one active device per participant is acceptable;
- `device_id` remains separate from participant (`ME`/`PARTNER`);
- bearer credentials can be revoked independently;
- a new install is a new device unless a future recovery protocol explicitly transfers identity.

Do not implement automatic history recovery from the server. That would silently turn the mailbox into the permanent archive the architecture explicitly rejects.

A future multi-device design would require per-device sender sequence numbers and an explicit policy for acknowledgements across multiple recipient devices. Do not prematurely implement that complexity now.

---

## 12. Retention findings

The system cannot simultaneously guarantee:

- server is only temporary;
- messages may remain unacknowledged forever;
- recipient can be offline indefinitely;
- no server storage bound exists.

Therefore a maximum retention window is mandatory.

The exact duration remains a product decision. The protocol must expose expiry as a first-class condition rather than pretending delivery is guaranteed after expiry.

Recommendation: choose a retention period comfortably longer than the expected offline period, document it clearly, and make expiration observable in the client rather than silently pretending synchronization succeeded.

---

## 13. E2E findings

The mailbox protocol can be implemented before the final cryptographic protocol if the payload is already opaque:

```text
ciphertext
ciphertext_version
sender_device_id
sender_seq
server_seq
```

Do not make the Worker depend on plaintext parsing beyond unavoidable envelope metadata/size/type validation.

Auth tokens are not encryption keys. A future E2E protocol must define device keys, relationship/session keys, rotation, revocation, and reinstall/recovery separately.

No custom cryptography should be implemented as part of C1/C2.

---

## 14. Decisions after C1

### Locked

- Workers + D1 + R2 remains the architecture.
- Phone SQLite remains permanent source of truth.
- No Durable Objects for MVP.
- Messages are immutable.
- Message IDs are client-generated and stable across retries.
- Sender sequence is durable per device.
- Server sequence is per relationship and allocated transactionally.
- Timestamps are metadata, not identity/order.
- ACK means durable local persistence.
- ACK is idempotent.
- Media bytes bypass Worker and use R2 directly.
- Presigned URLs are short-lived bearer capabilities.
- Human pairing code is not the credential.
- Device auth identity is separate from encryption identity.

### Still open

1. Maximum unacknowledged mailbox retention.
2. Whether strict server-side sender-sequence contiguity is required when HTTP requests arrive out of order.
3. Exact media upload table shape (`media_uploads` vs nullable attachment in `media_objects`).
4. Maximum photo/video sizes and multipart threshold.
5. Poison-message handling state/UX.
6. Relationship-end handling for already accepted mailbox messages.
7. E2E protocol/library.
8. Whether the MVP should support only one active device per participant (recommended) or multi-device from day one.

---

## 15. C1 completion criteria

C1 is considered complete because the major failure classes have explicit intended behavior and the architecture has no blocker requiring a different backend stack.

Before C2 (schema implementation), the remaining product-level decisions above should be resolved or explicitly given safe defaults. The implementation should turn the hard invariants in this document into automated tests.
